This page is for maintainers of weebo-stalwart. To install a release, see
[Install](/docs/guides/install).

Versions come from the commit history: commits follow Conventional
Commits (enforced by [cocogitto](https://docs.cocogitto.io/) on every
commit), and `cog bump --auto` derives the next version from them.

## What a release produces

For a tag `vX.Y.Z`, `publish.yml` calls weebo-operator-kit's reusable
`publish.yml`:

| Step | Gate / output |
| --- | --- |
| `version-check` | `Chart.yaml` `version` and `appVersion` and the Cargo workspace version equal the tag |
| `image` (×2) | `ghcr.io/batleforc/weebo-stalwart-operator:vX.Y.Z` (+ `latest`, Red Hat Hummingbird) and `…:vX.Y.Z-static` (+ `static`, optional: left out when it fails), `linux/amd64`, with SBOM and SLSA provenance, cosign-signed by digest |
| `chart` | `oci://ghcr.io/batleforc/charts/weebo-stalwart`, version `X.Y.Z`, cosign-signed by digest |
| `github-release` | The GitHub Release: `cog changelog` notes, the chart `.tgz`, `weebo-stalwart-crds.yaml` and its Sigstore bundle |

Each image is first built for amd64 and loaded locally, scanned by Grype
(HIGH/CRITICAL fail the job, accepted findings are `.grype.yaml`'s) and
smoke-run (`weebo-stalwart-importer --version`, which also proves the
importer ships in the image); only then is it pushed, and its pushed digest
is scanned and smoke-run again before it's signed.

## Bumping

`cog bump` runs `.hooks/bump-versions.sh`, which writes the version into
`Cargo.toml` (`[workspace.package]`), `Cargo.lock` and `Chart.yaml`
(`version` and `appVersion`), commits, tags and updates `CHANGELOG.md`.
Bumps are only allowed on `main` (`branch_whitelist` in `cog.toml`).

```bash
cog bump --auto --dry-run   # shows the next version
cog bump --auto             # bump commit + tag, signed by your git config
git push origin main --follow-tags
```

The pushed tag triggers `publish.yml`. To publish an existing tag again,
run `publish.yml` manually with that tag.

## Before releasing

| Check | Where |
| --- | --- |
| Lint, unit, contract and envtest tests, chart lint and smoke renders, audit | `ci.yml` (the kit's `checks.yml`), every push |
| Generated files up to date: CRDs, their chart copies, the docs' CRD and reference pages | `ci.yml` job `regen-and-diff` |
| The docs site builds and lints | `ci.yml` job `docs` |
| Both images build and run (`weebo-stalwart-importer --version`) | `ci.yml` job `image-build` |
| Against a real Stalwart v0.16.27: gateway, controllers, importer | `task test:live-stalwart` |

For the live suites: `task stalwart:container:start ENGINE=podman` (writes
`.stalwart-test.env`), `task test:live-stalwart`, then
`task stalwart:container:stop ENGINE=podman`.

## Supporting a new Stalwart release

The operator only writes to a server whose management schema hash it
knows (`SUPPORTED_SCHEMAS`, `crates/adapters-outbound/src/jmap/mod.rs`). A
Stalwart patch that keeps the schema needs no release; one that changes it
needs the contract and live suites run against the new image, then the
hash added, then a release — before the Stalwart upgrade reaches the
clusters.

## Changing the chart

- The chart is built on weebo-operator-kit's library chart
  (`weebo-operator-lib`, a dependency pinned to the kit's version):
  `templates/_params.tpl` holds what is Stalwart's own (kinds, admitted
  kinds, Stalwart egress). A change to a shared resource goes to the kit.
- The CRDs under `deploy/charts/weebo-stalwart/templates/crds/` are
  generated by `task recu` from `deploy/crd/`: never edit them.
- Every new value goes into `values.yaml` **and** `values.schema.json`.
- `task lint:helm` lints and renders the main value combinations.
- `task kit:sync TAG=vX.Y.Z` moves the crates, the kit's tasks, the
  reusable workflows, the library chart and the docs package to another kit
  release.

## The documentation site

This site is published to GitHub Pages by `docs-pages.yml` on every push to
`main` that touches `docs/` or the CRDs, and can be re-run by hand. It's a
static export; the workflow sets `DOCS_BASE_PATH` to `/weebo-stalwart` for
the project-site sub-path. Locally, `task docs` runs the dev server and
`task docs:build` builds and lints it at the root. The CRD pages and the
reference pages (reason codes, Events, metrics, resource budget) are
generated by `task recu`: never edit them by hand.
