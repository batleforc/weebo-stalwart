---
title: Service accounts
description: Give an application an SMTP account, an App Password and submission settings delivered to a Secret or Vault, and rotate it.
---

A `StalwartServiceAccount` is the account an application sends mail with:
an `x:Account` of type `User`, without any password, that authenticates
with an **App Password**. The operator has Stalwart generate the App
Password, and writes it with the SMTP submission settings to the CR's
`secretTargets`. Nobody copies a password by hand.

**It needs the instance's second key.** The App Password is created with
the instance's
[`appPasswordTokenSecretRef`](/docs/guides/connect-instance#the-app-password-key).
Without it, every `StalwartServiceAccount` of that instance fails with
`TokenSecretMissing`, before any account is created; the other kinds don't
need it.

## Why an App Password

When your users sign in through OpenID Connect, Stalwart's default
directory is the `Oidc` one, and on the community edition it serves every
domain: a password login goes to the identity provider and fails, and
Stalwart refuses to store a password at all ("Cannot set credentials for
accounts in an external directory"). App Passwords are checked before the
directory, so they work whatever it is. The operator therefore never writes
a password, with or without OpenID Connect.

## Declare one

Declare it next to the application, in its namespace (for instance in the
application's own chart):

```yaml
apiVersion: stalwart.weebo.io/v1alpha1
kind: StalwartServiceAccount
metadata:
  name: forgejo
  namespace: forgejo
spec:
  domainRef: { name: example.internal }   # a StalwartDomain
  name: forgejo                           # forgejo@example.internal (default: metadata.name)
  aliases: [noreply]                      # noreply@example.internal, used as From
  receive: false                          # a no-reply sender (default)
  secretTargets:
    - name: forgejo-smtp                  # a Secret in this namespace
```

```bash
kubectl -n forgejo get stalwartserviceaccount
```

```text
NAME      INSTANCE   ADDRESS                     READY   REASON       AGE
forgejo   main       forgejo@example.internal    True    Reconciled   3m
```

## What the application receives

Every target gets the same keys:

| Key | Value |
| --- | --- |
| `host` | the instance's `submission.host` (default `stalwart.mail.svc.cluster.local`) |
| `port` | the instance's `submission.port` (default `587`) |
| `security` | `starttls`, `tls` or `none` (the instance's `submission.security`) |
| `username` | the account's address, `forgejo@example.internal` |
| `password` | the account's App Password (`app_…`), generated by Stalwart |
| `from` | the first alias's address (`noreply@example.internal`), else the account's |

Mount them, or map them into the application's mailer settings: the
application logs in with `username` and `password` (`AUTH PLAIN`/`LOGIN`
after `STARTTLS`). Stalwart shows the App Password once, when it creates
it; the operator never logs it, never puts it in the status or in an
Event, and never reads it back.

## What the account can do

It logs in over **SMTP submission only**: IMAP, POP3 and ManageSieve logins
are disabled, and its App Password grants `authenticate` and `emailSend`
only. With `receive: false` (the default), delivery to it is
disabled as well; set `receive: true` when the application must receive
bounces or replies. Its aliases are local-parts of the same domain, usable as
sender. An alias containing `@` is refused (`InvalidSpec`).

## Secret targets

- **Kubernetes**: `{ name: <secret> }`, in the CR's own namespace (another
  namespace is refused). The Secret carries the annotation
  `stalwart.weebo.io/owner: StalwartServiceAccount/<namespace>/<name>`: a
  Secret owned by something else is never overwritten
  (`SecretTargetFailed`).
- **Vault**: `{ backend: vault, name: smtp }`, without `path`. It is written
  to `<pathPrefix>/<namespace>/smtp` under the instance's mount — the only
  Vault path the operator's role needs (see
  [Where secrets go](/docs/guides/connect-instance#where-secrets-go)). Any
  other name, or a `path`, is refused at admission. Vault targets need a
  `StalwartInstance` with a `secretStore.vault`.
- **None listed**: one Kubernetes Secret named after the CR, in its
  namespace — only accepted when the instance's default backend is
  `kubernetes`.

```yaml
spec:
  secretTargets:
    - name: forgejo-smtp          # Kubernetes Secret
    - backend: vault
      name: smtp                  # <pathPrefix>/forgejo/smtp
```

## Rotation

A new App Password is created, the previous one revoked in the same call,
and written to every target:

- when the account is created;
- when the annotation `stalwart.weebo.io/rotate-secret` takes a new value
  (any string: a date, a ticket number) — the value served is recorded in
  `status.lastRotation`, so the same value never rotates twice;
- when a target lost it (a Secret deleted, a Vault value removed);
- after a reconcile that failed to write it (`SecretTargetFailed`), since a
  target may then hold an outdated one.

```bash
kubectl -n forgejo annotate stalwartserviceaccount forgejo \
  stalwart.weebo.io/rotate-secret="$(date +%F)" --overwrite
```

The operator's App Passwords carry the description `weebo-stalwart`: a
rotation revokes those, and only those. Other App Passwords on the account
(created in the web interface) are kept.

## Deletion

`deletionPolicy: Delete` (the default) deletes the account and the secrets
the CR wrote. `Orphan` leaves both in place.

## Already in Stalwart

The account is read by `status.remoteId`, never adopted by name: an address
already taken in Stalwart fails with `StalwartObjectAlreadyExists` until the
[importer](/docs/guides/migration) links it to this CR. A linked service
account always gets an App Password of the operator's on its first
reconcile, written over what another tool wrote in its targets, so remove
that tool's resource first. A password that tool set on the account is
left alone: it stops working once the default directory is OpenID Connect,
or remove it in the web interface.
